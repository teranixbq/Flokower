# 002. Business Logic & Analysis - Flokower App

## 📊 Bisnis Model Overview

### Target Market
**UMKM Florist / Toko Bunga Krusiatif**
- Contoh: Bucket Kreatif
- Kebutuhan utama: Manajemen stok bahan baku bunga dan produk jadi
- Masalah yang dihadapi: Sulit tracking stock, sering over/under stock, manual record penjualan

### User Persona
**Primary User:** Owner/Staff toko bunga
- Umur: 25-45 tahun
- Tech-savvy level: Basic (familiar dengan smartphone)
- Kebutuhan: Simple, cepat, tidak ribet
- Pain points: 
  - Lupa catat stok berkurang
  - Stock material tidak akurat
  - Susah track order yang sedang dikerjakan
  - Tidak tahu kapan harus restock

## 🔍 Masalah Bisnis Utama & Solusi

### MASALAH 1: Stock Tracking yang Tidak Akurat

**Deskripsi Masalah:**
Di toko bunga tradisional, owner sering lupa catat pengurangan stok material setiap kali ada pesanan selesai. Hasilnya:
- Data sistem vs realita berbeda jauh
- Saat mau terima order baru, ternyata bahan habis tapi sistem masih show tersedia
- Customer kecewa karena order dibatalkan di tengah jalan
- Pembelian material berlebihan atau kurang

**Analisis Dampak:**
- ✅ **Dampak Keuangan:** Kehilangan revenue dari order yang dibatalkan
- ✅ **Dampak Operasional:** Staff bingung mana material yang benar-benar ready
- ✅ **Dampak Customer:** Trust issue, customer komplain
- ✅ **Dampak Bisnis:** Loss estimated Rp 500.000 - 2.000.000 per bulan dari canceled orders

**Solusi Flokower:**
1. **Soft Stock Reservation System:**
   - Saat order dibuat → Status `in_progress` → Material langsung di-reserve
   - Sistem otomatis kurangi dari "available stock"
   - User lain bisa lihat stok berkurang secara real-time

2. **Final Deduction on Completion:**
   - Baru dikurang permanen saat order diselesaikan
   - Jika dibatalkan → Reserve dilepas, stok kembali normal
   - History lengkap semua perubahan

3. **Adjustment Log:**
   - Ada fitur koreksi manual jika physical count beda dengan system
   - Semua adjustment tercatat dengan reason & timestamp
   - Bisa filter berdasarkan tanggal/user

**Business Value:**
- ⬆️ Akurasi stock meningkat dari ~60% menjadi 98%+
- ⬇️ Canceled orders turun drastis
- ⏱️ Hemat waktu checking stock manual
- 💰 Revenue protection: Gak ada lost opportunity karena salah data

### MASALAH 2: Duplikasi Proses Order

**Deskripsi Masalah:**
Saat klik tombol "Complete" untuk selesaikan order:
- Tombol loading lama banget (3-5 detik)
- User gak sabar, mikir error → Klik lagi!
- Hasilnya: Order completed 2x
- Stok terpotong 2x
- Revenue tercatat 2x
- Uang masuk tapi material keluar lebih banyak = rugi

**Analisis Dampak:**
- ✅ **Dampak Keuangan:** Revenue overreported (false positive)
- ✅ **Dampak Stock:** Material actual > system deduction
- ✅ **Dampak Report:** Laporan bulanan tidak akurat
- ⚠️ **Dampak Psikologis:** Owner curiga ada pencurian atau glitch sistem

**Solusi Flokower:**
1. **Loading State Protection:**
   ```
   User klik Complete:
   1. Tombol langsung disable
   2. Text berubah jadi "Processing..." + spinner berputar
   3. Animasi loading ditampilkan
   4. User TIDAK BISA klik lagi sampai selesai
   
   Setelah API response:
   - Success: Muncul "✅ Completed", button mati permanen
   - Error: Button enable kembali + pesan error jelas
   ```

2. **Button State Machine:**
   - IDLE → Loading → Success/ERROR (hanya 1 path forward)
   - Re-click during loading: AUTO-reject, tidak proses apapun

3. **Server-Side Validation:**
   - Double-check status sebelum proses
   - Jika sudah completed → Auto-reject second request
   - Log all attempts untuk audit trail

**Business Value:**
- ✅ No more duplicate revenue recording
- ✅ Stock accuracy maintained
- ✅ User confidence tinggi (system reliable)
- ⏱️ UX lebih smooth tanpa confusion

### MASALAH 3: Multiple Concurrent Orders Race Condition

**Deskripsi Masalah:**
Jika ada 2 staff yang handle order bersamaan:
```
Situation:
- Material: 100 tangkai mawar merah
- Staff A: Buat order Teddy Bear (butuh 10 tangkai) → in_progress
- Staff B: Buat order Teddy Bear lagi (butuh 10 tangkai) → in_progress
- Both berhasil karena: 
  * Staff A belum reserve stock
  * Staff B belum reserve stock
  * Total needed: 20, tapi available: 100 ✓ OK
  
Lalu saat completion:
- Staff A complete → Kurangi 10 tangkai (stock now: 90)
- Staff B complete → Coba kurangi 10 tangkai... 
  WAIT! Actually only 85 left (some used for other orders)
  Result: Stock negative! System chaos!
```

**Analisis Dampak:**
- ✅ **Dampak Operasional:** Material shortage saat produksi
- ✅ **Dampak Customer:** Order gagal karena bahan tidak cukup
- ✅ **Dampak Keuangan:** Cost overrun (harus beli emergency material)
- ❌ **Data Integrity:** Stock history corruption

**Solusi Flokower:**
1. **Real-Time Stock Sync:**
   - Menggunakan Firestore real-time listeners
   - Setiap ada update stock → Broadcast ke semua connected users
   - User B bisa LIHAT langsung bahwa Staff A udah reserve 10 tangkai
   - Available stock for Staff B: 100 - 10 = 90

2. **Reservation Before Creation:**
   ```javascript
   Function: createOrder(product):
     1. Check stock availability FIRST
        For each ingredient:
          available = currentStock - reservedStock
          if available < needed:
            BLOCK creation + show alert "Insufficient stock!"
            STOP
        
     2. If ALL ingredients sufficient:
        - Create transaction record with status 'in_progress'
        - IMMEDIATELY reserve materials
        - Update reservedQuantity in Firestore
        - Broadcast real-time update to all users
        
     3. User sees:
        - Order created successfully
        - Stock updated in dashboard (decreased by reserved amount)
        - Other users see this change instantly
   ```

3. **Atomic Transaction Processing:**
   ```javascript
   Function: completeTransaction(transactionId):
     Uses Firestore runTransaction() for atomicity
     
     Within single transaction scope:
       a. Verify transaction status = 'in_progress'
       b. Get current material quantities
       c. Verify still enough stock NOW (not just when created!)
       d. IF insufficient at completion time:
          - ROLLBACK everything
          - Show error: "Stock became unavailable, please check"
       e. IF sufficient:
          - Deduct materials permanently
          - Clear reservation
          - Mark transaction as completed
          - All changes happen together (all-or-nothing)
   ```

**Business Value:**
- ✅ Zero race conditions
- ✅ Accurate stock visibility across multiple users
- ✅ Fair resource allocation (first come, first served)
- ✅ Prevent negative stock scenarios
- ✅ Real-time collaboration without conflicts

### MASALAH 4: Wrong Material Mapping

**Deskripsi Masalah:**
Product template punya mapping standar, tapi reality有时候 berbeda:
```
Standard Mapping for "Rose Bouquet":
- 10 rose petals (lembar)
- 5 fern leaves (lembar)

Actual Production:
- Staff pakai 8 whole rose stems (tangkai) instead of petals
- Plus some green foam filler (tidak ada di mapping)
- Fern leaves not used at all

Result:
- System deduct wrong materials
- Actual stock depleted ≠ system prediction
- Rose petals inventory stays high (should be lower)
- Fern leaves shows zero movement (actually sometimes used)
- Whole rose stems not tracked properly
```

**Analisis Dampak:**
- ✅ **Inventory Accuracy:** Data material sangat wrong
- ✅ **Restocking Decisions:** Beli material yang salah
- ✅ **Cost Calculation:** HPP tidak akurat
- ✅ **Production Efficiency:** Confused planning next batch

**Solusi Flokower:**
1. **Custom Ingredient Override Per Transaction:**
   ```javascript
   Transaction Schema:
   {
     productId: "rose_bouquet",
     useCustomMapping: boolean,      // True = override default
     standardIngredients: [
       {materialId: "rose_petals", quantityNeeded: 10},
       {materialId: "fern_leaves", quantityNeeded: 5}
     ],
     
     customIngredients: [  // Only populated if useCustomMapping = true
       {
         materialId: "rose_stems_whole",
         quantity: 8,
         note: "Using stems instead of petals today"
       },
       {
         materialId: "green_foam",
         quantity: 1,
         note: "Extra filler material"
       }
     ]
   }
   ```

2. **UI Implementation:**
   ```
   Create Order Screen Flow:
   
   Step 1: Select product "Rose Bouquet"
     → Shows preview: "Requires: 10 rose petals + 5 fern leaves"
     → Shows stock indicators: 🟢 Green (sufficient)
   
   Step 2: Toggle "Customize materials used"
     ON/OFF switch
   
   Step 3: If ON:
     - Hide standard ingredients preview
     - Enable manual ingredient editor
     - Add row: Select material from dropdown + input quantity
     - Can add extra materials not in standard
     - Optional: Add notes per material
   
   Step 4: Recalculate stock validation
     - Against CUSTOM ingredients list
     - Not against standard
   
   Step 5: Create transaction
     - Save both standard AND custom mapping
     - Track which was actually used
   ```

3. **Transaction History Visibility:**
   ```
   Sales Report Row:
   ├─ Order #123 - Rose Bouquet × 1 (Rp 150,000)
   │  ├─ Materials Used (CUSTOM):
   │  │  ├─ 🌹 Rose Stems: 8 pieces ← Different from standard!
   │  │  └─ 🧦 Green Foam: 1 piece ← Extra material
   │  │  
   │  ├─ Stock Impact:
   │  │  ├─ Reserved: rose_whole (-8), foam_green (-1)
   │  │  └─ Released: fern_leaves (+5) ← NOT actually used
   │  │  
   │  └─ Notes: "Customer wanted stem-based arrangement"
   ```

**Business Value:**
- ✅ Flexibility dalam production tanpa rigid templates
- ✅ Historical accuracy: See EXACTLY what was used
- ✅ Better cost tracking per transaction
- ✅ Learning tool: Identify patterns in material usage variations
- ✅ Adaptability: Handle special requests/custom orders

### MASALAH 5: Orphaned In-Progress Orders

**Deskripsi Masalah:**
Staff mulai buat order → Status jadi `in_progress` → 
Lanjut kerja tapi interrupted (telepon, customer datang, makan siang)
→ Lupakan order tersebut
→ Order stuck in `in_progress` forever
→ Materials remain "reserved" but never used
→ Dashboard metrics confusing (shows "active orders" that don't exist)

**Analisis Dampak:**
- ⚠️ **Confusing Metrics:** Dashboard shows fake active orders
- ⚠️ **Resource Blockage:** Materials appear unavailable but aren't being used
- ⚠️ **UX Frustration:** Staff wonder why these orders won't disappear
- ⚠️ **Capacity Planning:** Cannot trust "in progress" count for staffing

**Solusi Flokower:**
1. **Reminder Notification System:**
   ```
   Auto-scheduled notifications:
   
   T+2 hours (after order creation):
     Push notification: 
       "Your order #123 (Teddy Bear) is still in progress?
        Tap to continue working or cancel."
    
   T+12 hours:
     Push notification:
       "Don't forget about order #123!
        It's been 12 hours. Complete or cancel to free up materials."
    
   T+24 hours:
     Warning push:
       "Order #123 will auto-cancel in 1 hour due to inactivity.
        Tap here to extend deadline if still working on it."
   ```

2. **Dashboard Highlighting:**
   ```
   Home Dashboard Section:
   ═══════════════════════════════════════
   🔴 URGENT: Orders Overdue (>6 hours)
   ═══════════════════════════════════════
   
   [Quick Action Card]
   Order #123 - Teddy Bear Bouquet × 1
   Started: 8h 23m ago
   
   Materials reserved:
   ├── 🌹 Rose Petals: 10 leaves
   └── 🍃 Fern Leaves: 5 leaves
   
   [✓ Complete]  [✗ Cancel]
   
   (Direct actions without opening detail view)
   ```

3. **Auto-Cancel Mechanism:**
   ```javascript
   Background Job Schedule:
   Run daily at 2 AM (low traffic time)
   
   Logic:
   Find all orders where:
     status = 'in_progress' AND
     startedAt < Now() - 48hours
   
   For each orphaned order:
     1. Send final warning notification (1 hour before cancel)
     2. After 1 hour timeout:
        - Automatically cancel
        - Release all reserved materials
        - Set cancelledAt timestamp
        - Reason: "Auto-cancelled: timeout exceeded"
        - Notify admin via email/notification
   
   Exception handling:
     - If order modified within 1 hour of auto-cancel:
       → Pause and wait another 24 hours
       → Assume user still actively working
   ```

**Business Value:**
- ✅ Cleaner dashboard metrics (only REAL active orders)
- ✅ Resources freed automatically (no manual cleanup needed)
- ✅ Staff reminded to finish or abandon orders
- ✅ Historical record of abandoned orders for analysis
- ✅ Peace of mind: System self-maintains itself

### MASALAH 6: Initial Stock Input Errors

**Deskripsi Masalah:**
Day 1 setup: Owner input 100 tangkai mawar merah
Reality: Only have 80 tangkai physically (10 already damaged/lost before entry)
Problem: All future calculations based on WRONG baseline!
- Month 1: System says 50 left after sales (actual: 30 left)
- Month 2: System triggers low-stock alert too late
- Customer disappointed when can't fulfill order

**Analisis Dampak:**
- ❌ **Cascade Effect:** Wrong starting point → wrong everything downstream
- ❌ **Poor Decision Making:** Restock timing off, ordering wrong quantities
- ❌ **Loss of Trust:** User stop believing system data
- ❌ **Financial Impact:** Over/under purchasing leading to cash flow issues

**Solusi Flokower:**
1. **Initial Verification Workflow:**
   ```
   Step 1: Enter estimated initial stock
     - Create materials with placeholder quantities
     - Tag as "UNVERIFIED" with warning badge
   
   Step 2: Physical count period (7 days recommended)
     - Display prominent warning: "Pending physical verification"
     - Remind user via push notifications:
       * Day 1: "Don't forget to verify your initial stock!"
       * Day 3: "Still unverified - please count soon"
       * Day 6: "Last chance before full system activation"
   
   Step 3: Perform physical count
     - Compare actual vs system numbers
     - If DIFFERENT: Create adjustment record
       Type: "initial_verification"
       Quantity change: +/- difference
       Reason: "Initial setup correction"
       
     - If SAME: Mark as verified
   
   Step 4: Remove unverified flag
     - Badge disappears
     - System considers data accurate
   ```

2. **Adjustment History Tracking:**
   ```javascript
   Stock Adjustment Record:
   {
     id: "adj_123",
     materialId: "rose_red",
     adjustmentType: "correction",  // or "addition", "removal"
     quantityChange: -20,           // Negative = reduction
     previousQuantity: 100,
     newQuantity: 80,
     reason: "Initial setup verification - found fewer items",
     performedBy: "owner_admin",
     createdAt: "2024-01-15 10:30:00"
   }
   ```

3. **Visual Indicators:**
   ```
   Material List Item:
   
   ┌──────────────────────────────────────┐
   │ 🌹 Mawar Merah                       │
   │ Status: ⚠️ UNVERIFIED                │
   │ Quantity: 100 (pending count)        │
   │ Unit: tangkai                        │
   └──────────────────────────────────────┘
   
   Click "Verify Now" button:
     → Opens counting screen
     → Input actual physical count
     → System calculates difference
     → Creates adjustment record automatically
   ```

**Business Value:**
- ✅ Honest baseline data from day 1
- ✅ Transparency about uncertainty periods
- ✅ Educational process teaches proper stock management
- ✅ Audit trail for all adjustments (including corrections)
- ✅ Confidence built through verification process

## 💡 Business Intelligence Opportunities

### Metrics Worth Tracking Long-term

#### Operational Metrics
1. **Order Completion Rate:**
   - Formula: (completed_orders / total_orders) × 100
   - Target: >90%
   - Low rate indicates production issues or unrealistic capacity

2. **Average Production Time:**
   - Mean duration from `in_progress` to `completed`
   - Helps identify bottlenecks
   - Useful for pricing/time estimation

3. **Material Usage Variance:**
   - Difference between standard_mapping vs actual_custom_mapping
   - Reveals patterns in customization
   - Potential cost optimization opportunities

#### Financial Metrics
4. **Revenue per Product Type:**
   - Breakdown by bouquet category
   - Identifies best/worst performers
   - Guides marketing/promotion focus

5. **Material Cost Ratio:**
   - COGS / Revenue percentage
   - Monitors profitability trends
   - Early warning for cost inflation

6. **Cancellation Rate & Reasons:**
   - Percentage of orders cancelled vs completed
   - Categorize reasons: customer, material shortage, quality
   - Address root causes systematically

#### Inventory Metrics
7. **Stock Turnover Rate:**
   - How many times full inventory sold/replenished per month
   - High turnover = healthy business
   - Low turnover = excess inventory risk

8. **Low Stock Alert Accuracy:**
   - % of alerts that resulted in actual reorder
   - False positives waste time
   - False negatives cause missed sales
