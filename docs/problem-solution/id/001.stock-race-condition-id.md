# 001. Race Condition pada Stock Deduction - ID

## 📖 Deskripsi Masalah

### Situasi
Ketika ada beberapa staff yang melakukan order secara bersamaan untuk produk yang menggunakan bahan baku sama, dapat terjadi kondisi di mana:

```
Scenario Timeline:
─────────────────────────────────────────────
T+0s: Material "Mawar Merah" = 100 tangkai
     Dashboard shows: Available = 100

T+1s: Staff A membuat order Teddy Bear (butuh 10 tangkai)
     → Status: in_progress  
     → Sistem check: 100 >= 10 ✓ OK
     → Create transaction success
     
T+2s: Staff B juga buat order Teddy Bear (butuh 10 tangkai lagi)
     → Sistem check: Masih 100 (belum update!)
     → Status: in_progress
     → Create transaction success ← PROBLEM!
     
T+10s: Staff A complete order
     → Deduct 10 tangkai
     → Stock now: 90 tangkai
     
T+15s: Staff B complete order  
     → Coba deduct 10 tangkai
     → But actual available only 85 (ada order lain)
     → RESULT: Stock jadi NEGATIF! ❌
─────────────────────────────────────────────
```

### Siapa Terdampak:
- **Owner**: Revenue tercatat tidak akurat, stock history corrupted
- **Staff**: Confused kenapa system data berbeda dengan physical stock
- **Customer**: Order dibatalkan karena bahan habis padahal sistem show tersedia

### Kapan Terjadi:
- Saat multiple users buka aplikasi bersamaan
- Ketika order dibuat tanpa immediate stock reservation
- Network latency menyebabkan delayed state sync

## 🔍 Root Cause Analysis

### Technical Root Causes

#### 1. No Immediate Stock Reservation
```javascript
// BEFORE (Vulnerable):
async function createOrder(product) {
  // Only checks stock, doesn't reserve
  if (checkEnoughStock(product)) {
    return createTransaction('pending');  // Status doesn't reflect reality
  }
}

Problem:
- Stock checked but not locked/reserved
- Other users can see same "available" amount
- Multiple transactions can claim same resources
```

#### 2. Delayed State Synchronization
```javascript
// Firestore has asynchronous updates
materialRef.update({ quantity: newQuantity });

// Time gap between write and read propagation:
User A writes: T+0s (update initiated)
User B reads:  T+2s (still sees old value!)
              ↑ 2 second window for race condition
```

#### 3. No Atomic Transaction Wrapping
```javascript
// Stock deduction happens in separate operations:
Step 1: Update transaction status
Step 2: Deduct material stock  
Step 3: Clear reservation

// If Step 2 fails after Step 1 succeeds → Inconsistent state!
```

### Business Process Gaps

#### 1. No Real-Time Visibility
- Staff cannot see other people's active orders instantly
- Lack of communication channel about ongoing work
- Manual coordination inefficient and error-prone

#### 2. Missing Validation Layers
- Client-side validation only (can be bypassed)
- No server-side atomicity guarantee
- No post-operation integrity check

#### 3. No Conflict Resolution Strategy
- When conflict detected → Manual intervention required
- No automated rollback mechanism
- No alert system for异常情况

## ✅ Solusi yang Diimplementasikan

### Solution Architecture Overview

Implemented **Multi-Layer Protection System** dengan pendekatan defensive programming:

```
┌─────────────────────────────────────────────────────┐
│           LAYERED STOCK MANAGEMENT SYSTEM           │
├─────────────────────────────────────────────────────┤
│                                                     │
│  Layer 1: UI Prevention                             │
│  ├─ Disable submit button when stock low           │
│  └─ Show real-time availability indicators         │
│                                                     │
│  Layer 2: Reservation Mechanism                     │
│  ├─ Immediate reserve when order created           │
│  └─ Broadcast to all connected clients             │
│                                                     │
│  Layer 3: Atomic Processing                         │
│  ├─ Firestore runTransaction() wrapper             │
│  └─ All-or-nothing execution                       │
│                                                     │
│  Layer 4: Final Validation                          │
│  ├─ Re-check stock at completion time              │
│  └─ Rollback if insufficient                       │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### Layer 2: Soft Stock Reservation System

**New Data Model:**
```typescript
// Material Schema Update
interface Material {
  id: string;
  name: string;
  unit: "lembar" | "tangkai";
  
  // NEW FIELDS ADDED
  currentQuantity: number;       // Physical stock count
  reservedQuantity: number;      // Reserved by in-progress orders

// Transaction Schema Enhancement
interface Transaction {
  id: string;
  status: 'in_progress' | 'completed' | 'cancelled';

    quantityReserve: number;   // Reserved amount
    quantityActual: number?;   // Actual deducted (set on completion)

}
```

**Reservation Logic:**
```typescript
// When order is CREATED (status = 'in_progress'):
async function reserveMaterials(transaction) {
  const batch = firestore.batch();
  
  // For each ingredient needed
  for (const ingredient of transaction.ingredients) {
    const materialRef = doc(firestore, 'materials', ingredient.materialId);
    
    // Increment reserved quantity
    batch.update(materialRef, {
      reservedQuantity: FieldValue.increment(ingredient.quantityNeeded),
      updatedAt: FieldValue.serverTimestamp()
    });
  }
  
  // Execute atomically
  await batch.commit();
  
  // Trigger real-time broadcast to all listeners
  await broadcastStockUpdate(transaction.materialsUsed);
}
```

**Real-Time Sync Implementation:**

#### Layer 3: Atomic Transaction Processing

**Completion Flow:**
```typescript
async function completeOrder(transactionId: string) {
  try {
    // Wrap ALL operations in single transaction
    const result = await firestore.runTransaction(async (transaction) => {
      
      // STEP 1: Get and validate transaction state
      const txDoc = await transaction.get(txRef(transactionId));
      const txData = txDoc.data();
      
      if (txData.status !== 'in_progress') {
        throw new Error(`Cannot complete ${txData.status} order`);
      }
      
      // STEP 2: Verify materials still available NOW (not just when created!)
      for (const usage of txData.materialsUsed) {
        const materialDoc = await transaction.get(materialRef(usage.materialId));
        const material = materialDoc.data();
        
        const availableNow = material.currentQuantity - material.reservedQuantity;
        
        if (availableNow < usage.quantityReserve) {
          throw new Error(
            `Insufficient stock for ${usage.materialId}. ` +
            `Need: ${usage.quantityReserve}, Available: ${availableNow}`
          );
        }
      }
      
      // STEP 3: Perform ALL updates atomically
      // a) Deduct material stocks permanently
      for (const usage of txData.materialsUsed) {
        const materialRef = materialRef(usage.materialId);
        
        transaction.update(materialRef, {
          currentQuantity: FieldValue.increment(-usage.quantityReserve),
          reservedQuantity: FieldValue.increment(-usage.quantityReserve),
          updatedAt: FieldValue.serverTimestamp()
        });
      }
      
      // b) Mark transaction as completed
      transaction.update(txRef(transactionId), {
        status: 'completed',
        completedAt: FieldValue.serverTimestamp(),
        materialsCompleted: txData.materialsUsed
      });
      
      // Return success
      return { success: true, completedAt: new Date() };
      
    });
    
    return result;
    
  } catch (error) {
    // Transaction rolled back automatically on any error
    console.error('Completion failed:', error);
    throw error;
  }
}
```

#### Layer 4: Post-Deduction Validation

**Safety Net Check:**
```typescript
// After every stock update, verify integrity
async function validateStockIntegrity() {
  const materials = await getAllMaterials();
  const issues = [];
  
  for (const material of materials) {
    // Never allow negative stock
    if (material.currentQuantity < 0) {
      issues.push({
        type: 'negative_stock',
        material: material.name,
        value: material.currentQuantity,
        severity: 'CRITICAL'
      });
      
      // Auto-rollback to zero
      await updateMaterialStock(material.id, 0);
      
      // Alert admin immediately
      sendCriticalAlert({
        title: 'Negative Stock Detected',
        message: `${material.name dropped to ${material.currentQuantity}`,
        timestamp: new Date()
      });
    }
    
    // Warn if below threshold unexpectedly
    if (material.currentQuantity < material.threshold) {
      notifyLowStock(material);
    }
  }
  
  return issues;
}

// Run periodically or after critical operations
setInterval(validateStockIntegrity, 5 * 60 * 1000); // Every 5 minutes
```

## 📝 Notes

### Lessons Learned

1. **Defensive Programming Pays Off**
   - Multiple validation layers prevent catastrophic failures
   - Cost of implementation justified by risk reduction
   
2. **Real-Time Visibility is Critical**
   - Users need instant feedback on system state
   - Transparency builds trust in automation

3. **Atomic Operations Are Non-Negotiable**
   - Always wrap related database operations together
   - Firestore transactions are free and fast enough

4. **Monitoring Prevents Silent Failures**
   - Automated validation catches issues early
   - Alert systems ensure human oversight when needed
